## 摘要
使用大语言模型（LLMs）实现优化建模自动化是通往可扩展决策智能的一条极具前景的路径，但现有方法要么依赖于基于闭源 LLM 构建的智能体流水线（具有高推理延迟），要么使用昂贵的步骤监督微调较小的 LLM，而这往往会过拟合到单一的求解器 API。受具有可验证奖励的强化学习启发，我们提出了执行验证优化建模（EVOM），这是一种将数学规划求解器视为确定性交互式验证器的执行验证学习框架。给定自然语言问题和目标求解器，EVOM 生成特定于求解器的代码，在沙箱环境中执行，并将执行结果转换为标量奖励，通过 GRPO 和 DAPO 在“生成-执行-反馈-更新”的闭环过程中进行优化。这种仅基于结果的表述消除了对步骤级监督的需求，并通过切换验证环境而非重建求解器特定数据集，实现了跨求解器的泛化。在 NL4OPT、MAMO、IndustryOR 和 OptiBench 上针对 Gurobi、OR-Tools 和 COPT 的实验表明，EVOM 的表现达到或超过了经过步骤监督微调（SFT）的模型，支持零样本求解器迁移，并通过在目标求解器后端下持续训练实现了有效且低成本的求解器适配。

## Abstract
Automating optimization modeling with LLMs is a promising path toward scalable decision intelligence, but existing approaches either rely on agentic pipelines built on closed-source LLMs with high inference latency, or fine-tune smaller LLMs using costly process supervision that often overfits to a single solver API. Inspired by reinforcement learning with verifiable rewards, we propose Execution-Verified Optimization Modeling (EVOM), an execution-verified learning framework that treats a mathematical programming solver as a deterministic, interactive verifier. Given a natural-language problem and a target solver, EVOM generates solver-specific code, executes it in a sandboxed harness, and converts execution outcomes into scalar rewards, optimized with GRPO and DAPO in a closed-loop generate-execute-feedback-update process. This outcome-only formulation removes the need for process-level supervision, and enables cross-solver generalization by switching the verification environment rather than reconstructing solver-specific datasets. Experiments on NL4OPT, MAMO, IndustryOR, and OptiBench across Gurobi, OR-Tools, and COPT show that EVOM matches or outperforms process-supervised SFT, supports zero-shot solver transfer, and achieves effective low-cost solver adaptation by continuing training under the target solver backend.

### 2. 方法论：EVOM 框架
*   **核心思想**：提出 **EVOM (Execution-Verified Optimization Modeling)**，将求解器作为环境反馈的来源，构建“生成-执行-反馈-更新”的闭环学习系统。
*   **关键技术细节**：
    *   **求解器条件化（Solver-Conditioning）**：在 Prompt 中明确指定目标求解器（如 Gurobi, OR-Tools, COPT），使模型学习特定 API 的用法。
    *   **输出协议**：强制模型输出结构为 `<think>推理过程</think> <code>代码</code>`。
    *   **沙箱执行系统**：在隔离环境中运行生成的 Python 代码，捕获执行状态（成功/失败）、求解状态（最优/不可行）和目标函数值。
    *   **奖励设计**：
        *   **格式奖励 ($r_{fmt}$)**：检查输出是否符合 XML 标签规范。
        *   **结果奖励 ($r_{ans}$)**：仅根据执行结果与标准答案（Ground Truth）的数值差异（或状态一致性）给予奖励，不参考任何中间代码。
    *   **算法流程**：使用 **GRPO**（组相对策略优化）或 **DAPO**（解耦剪裁与动态采样）进行策略更新。通过组内对比（Group-relative）来估计优势函数，无需额外的 Critic 模型。

### 6. 主要结论与发现
*   **无需过程监督**：EVOM 仅靠结果奖励就能达到或超过需要昂贵过程标注的 SFT 模型。
*   **强大的泛化性**：EVOM 学习的是底层的数学逻辑而非单纯的代码模仿，因此在跨求解器迁移（Zero-shot Transfer）中表现远优于 SFT 模型。
*   **推理的重要性**：强化学习能够激发出模型的推理能力，`<think>` 块作为“内部工作空间”，对解决复杂逻辑问题至关重要。
*   **低成本适配**：对于新求解器，只需切换执行环境并进行少量 RL 训练即可快速适配，无需重建数据集。

### 7. 优点
*   **数据效率高**：摆脱了对“推理链”标注的依赖，只需“问题-答案”对即可训练。
*   **解耦建模与语法**：通过环境反馈，成功将通用的数学建模能力与特定求解器的 API 语法进行了有效结合。
*   **实战导向**：沙箱执行确保了生成的代码不仅逻辑正确，而且在语法上是可运行的。

### 8. 不足与局限
*   **逻辑错误瓶颈**：错误分析显示，虽然 RL 显著减少了变量定义和语法错误，但对于**深层语义约束错误**（即理解错题意或漏掉约束）的提升相对有限。
*   **依赖 Ground Truth**：训练仍需要已知最优解的问题集，对于完全未知的开放式优化问题，如何构建奖励信号仍是挑战。
*   **冷启动摩擦**：对于模型完全没见过的求解器 API，仍需要极少量的（约 100 条）SFT 数据来引导模型跨越“无法生成可执行代码”的初期阶段。
